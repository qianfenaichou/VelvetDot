# 02 环境部署与运行验证

在一台 Linux 机器上，从三份源码、一个测试镜像和一套工具链开始，到香山模拟器打印出一行 hello 身份串，需要哪些步骤，每步靠什么标志确认成功。这一章给出这条路径上的版本锁定、构建顺序、冒烟方法和失败边界。后续的差分验证、性能测量与覆盖率都依赖这条构建流程产出的模拟器；这一步不通，后面的数字就没有载体。

## 2.1 为什么环境步骤排在最前

香山（一个开源 RISC-V 处理器）用 Chisel（一种用 Scala 写的硬件描述语言）描述。Chisel 经 Mill（Scala 构建工具）生成 SystemVerilog（寄存器传输级的硬件描述，简称 RTL），再由 Verilator（把硬件描述翻译成 C++ 的仿真器）编译成可在普通服务器上执行的程序。NEMU 是香山的差分测试参考模型，差分测试把同一条指令分别交给香山和 NEMU，逐条比较寄存器结果。工具或源码版本一变，被比较的对象就变。环境步骤因此排在最前：它把后续结果绑定到一套确定的工具和源码上。

首轮只读探测在 2026-11-01 15:02:22 执行，报告 Verilator、Yosys、Mill 与 RISC-V 交叉工具链（在 x86 主机上生成 RISC-V 程序的编译器）缺失，Java 为 8。2026-11-05 09:27:24 的探测才整体通过。补齐这些工具的路径见 2.2。这一步不产生处理器结果，但它决定后面每一步能不能开始。

## 2.2 工具基线

作业跑在共享超算的一台 CPU 节点上。集群为华东一区【昆山】超算，作业调度器版本 22.05.8（`sinfo -V` 输出），共 4 个分区且都没有默认分区，提交时必须写明 `-p`；本章的构建、冒烟与回归都落在 CPU 分区 `kshcnormal`，该分区 4011 个节点。单节点 32 个物理核（4 路 × 8 核，无超线程）、126500 MB 内存，系统 CentOS 7.6、内核 `3.10.0-957.el7.x86_64`。这组数字来自 2026-10-30 的 `sinfo` 与 `scontrol show node` 读数，记录见 `design/hpc/_recon/kunshan-env.md:64-79`（分区）与 `:129-160`（节点规格）；记录里没有 CPU 型号字符串，只有核数与路数，所以这里也不写型号。换一台机器复现，要先核对是否同档配置；本章没有第二台机器的执行记录，边界见 2.6。

## 2.3 从源码到模拟器

三份源码在 `versions.env` 里锁定：XiangShan `a4eeaab`、yunsuan `9559211`、NEMU `a683e0b`。该文件还写了一行 `TAG=baseline-20261101`。本仓库的克隆里没有这个标签（`git tag -l` 输出为空），锁定值只能按提交号读。yunsuan 是香山的向量运算子模块，vdot 的归约树加在这里。锁定值是基线提交；vdot 的改动以补丁叠在基线上，实施后的提交号见第 1 章。

构建分两段。先编 NEMU，得到 `riscv64-nemu-interpreter-so`，它是差分测试的参照；NEMU 用主机 GCC 编译成共享库，emu（模拟器）在运行时加载它。再在 XiangShan 目录执行 `make emu`。Mill 驱动 Chisel 生成 SystemVerilog，Verilator 生成 C++，主机 GCC 编译成 `build/emu`。`10-build-emu.sh` 把两段包在一起，并记录检查项：版本是否与锁定值一致、参考模型是否存在、`nm`（读符号表的工具）能否在参考模型里找到 `exec_vdot`、`make emu` 是否返回 0、`build/emu` 是否可执行。版本不一致默认只记警告，加 `--require-pin` 才判失败。

`nm` 命中 `exec_vdot` 2 行，说明 vdot 的参考模型编进了 .so，不只是存在于源码里。归档记录里，性能复跑所用 emu 的 md5 为 `fd65ca4af946bff28a7e2f1ce6c7bd01`。差分全量运行的日志首行记 `max_instr=200000000`；冒烟那次运行的 JSON 没有这个字段，日志也没记命令行，所以冒烟实际生效的上限没有归档证据，这里不给数。

构建期有两个常见故障。xPack RISC-V GCC 默认 `ilp32` ABI（函数调用与数据布局的约定），而 nexus-am 的 Makefile 只传 `-march`，需要包装器补 `-mabi=lp64`。`rocket-chip` 的 `cde` 与 `hardfloat` 子模块必须非空，空目录会让脚本先试 `make init`，仍为空则停止构建。两项都会让构建停在中途。

## 2.4 hello 冒烟证明了什么

冒烟是最小可运行检查：镜像能载入、程序能跑完、输出符合预期。构建成功只说明二进制生成，hello 冒烟说明它真的在执行指令。镜像是 nexus-am 裸机程序（不跑操作系统），启动后输出一行 `hello xiangshan, I am XinXiangXiangRong, IP: <执行节点地址>`，然后以 `HIT GOOD TRAP` 退出。程序短、输出固定，能先暴露取指、译码、执行、访存和退出路径的问题；直接跑 vdot 用例时，环境故障与语义故障难以分开。

这行字把整条路径串起来：RISC-V 交叉编译器（在 x86 主机上生成 RISC-V 程序）产出镜像。emu 载入镜像，核取指、译码、执行，程序访问输出设备，结束时触发退出陷阱。取指、译码、执行或输出任一环坏了，这行字都不会出现；退出路径坏了，`HIT GOOD TRAP` 不会出现。`ABORT` 或 `HIT BAD TRAP` 表示执行出错。

地址在编译期注入。nexus-am 没有网络栈，运行期拿不到本机地址；镜像编译时把执行节点 `hostname -I` 的第一个字段写进字符串，换节点重编，字符串就跟着换。

官方交付物 1.1 的原文只要求输出 `hello xiangshan, I am xxx, IP address`，`xxx` 换成团队或个人标识，没有规定地址格式。本项目的检查比原文严：另外要求点分四段、每段 0～255，并拒收 `0.0.0.0`、广播地址、回环地址与 169.254 开头的自动配置地址（`10-build-emu.sh:343-355`）。这条附加检查是自设的，不是官方要求。它防的是只匹配 `hello` 字样就把占位地址的输出记成通过。

## 2.5 四步复现

表 02-2 把这条路径压成四步，按依赖顺序排列；每步成功标志都取自程序实际会写出的字符串或字段。

表 02-2　四步复现与成功标志

| 步骤 | 命令 | 成功标志 | 产物 |
|---|---|---|---|
| 环境自检 | `bash 00-env-check.sh --probe` | JSON 的 `status` 为 `通过` | `results/env/00-env-<runid>.json` |
| 构建与冒烟 | `10-build-emu.sh --src-root <src> --image <hello.bin>` | 退出码 0，日志含身份串与 `HIT GOOD TRAP` | `results/emu/10-build-<runid>.json` |
| 金模型自检 | `python3 -I design/verify/vdot_model_test.py` | 输出 `ALL TESTS PASSED` | 终端输出 |
| 主回归 | `20-run-difftest.sh --full` | JSON 的 `status` 为 `通过` | `results/difftest/20-full-<runid>.json` |

金模型是规格的独立软件实现，不经过 RTL 仿真。它先通过，后面的逐条比对才有可信的参照。前三步是单次检查，第四步才跑完整清单。这套流程在昆山集群的 CPU 分区 `kshcnormal` 上执行。主回归清单 30 例。另有 224 例扩容清单单独运行，一次从开始到结束的墙钟时间为 1 h 39 min 49 s（单次，起止时间取自 `results/difftest/extra/94-extra-20261108T014445.json`）。这是单次观测，不是每一步的固定开销。通过数、用例构成与空绿防护（防止测试全过但没比较结果）见第 7 章。

产物要分开看。环境自检、构建冒烟、主回归三步都写 JSON 或日志。金模型自检没有归档的 JSON 或日志：封装它的 `30-golden-regress.sh` 头注写着「待跑」，`results/` 下也没有 `golden/` 目录。因此归档记录覆盖三步，不覆盖金模型自检。

## 2.6 复现边界

身份串那次冒烟没有从源码重建 emu。`make emu` 使用了此前构建的产物，`build_emu=达标` 只证明 `build/emu` 存在且可执行。这一章因此不能给出一次干净构建的耗时，也不能把这次冒烟当作完整构建的验证。

仓库里保存的 hello 镜像不是当次运行的那份，镜像内的地址也不是执行节点地址。要复现这行身份串，必须在执行节点内重新编译镜像。

这一章没有在本地重跑构建、冒烟和回归，版本、时间与产物都引用归档记录。构建与回归只在昆山集群上跑过，没有第二台机器的执行记录；本机没有 `build/emu`，仓库里的 nexus-am 源码树为空，所以“换一台机器照样跑通”本章给不出证据。工具探针只覆盖可执行文件与版本号，不覆盖编译器行为、系统库差异和节点负载。流程只覆盖 x86 Linux 上的 CPU 仿真，不覆盖 FPGA 原型与硅后实测。

hello 冒烟只证明一条小程序能从入口跑到正常退出，不证明 vdot 的语义、向量寄存器比对或性能。这些结论分别由第 4、7、8 章给出。
